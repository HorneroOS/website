# Internationalization (English / Spanish): research and plan

Status: research and decision record. The site is English-only today; this
page decides how Spanish arrives without breaking the "website follows
product" rule.

## What exists

| Layer | State | Source |
| --- | --- | --- |
| Shell UI | Every user-visible string goes through `qsTr()`; enforced by `tests/test_welcome_static.py` for the Welcome Center | HorneroOS/docs `development/i18n.md` |
| Documentation | English first, organization-wide; no translation workflow | HorneroOS/docs `development/i18n.md`, HorneroOS/.github |
| Product metadata | Preset names/descriptions (`presets/*.json` `_name`, `_description`) and theme pack descriptions (`theme.json`) are English-only strings | HorneroOS/shell, HorneroOS/config |
| Website | Hand-written pages (home, install, companion, roots) plus pages generated from product metadata (layouts, themes, releases) and the docs | `docs/PRODUCT_DATA.md` |

Reference projects (W1/W-delta research, 2026-10-02): Omarchy keeps its
manual English-only ("until the separate manual workflow is implemented",
`docs/translations.md:134`) while site chrome is translated; Ryoku and
DankMaterialShell are English-only.

## The constraint that decides the design

Half of this site is generated from product data. Translating those strings
in the website would create a second source of truth that drifts every time
a preset or theme changes, which is exactly what `data:check` exists to
prevent. Spanish for generated pages must therefore come from the product.

## Plan

1. **Now (no Spanish yet).** Keep page copy in the page files and product
   facts in `src/data/product`; avoid string concatenation across sentences
   so each sentence can become one translation unit later.
2. **Spanish chrome and hand-written pages.** Astro's built-in i18n routing
   (`i18n: { locales: ['en', 'es'], defaultLocale: 'en', routing: {
   prefixDefaultLocale: false } }`): English stays at `/`, Spanish at
   `/es/`. Translate home, install, companion and roots first. Add
   `hreflang` alternates and the sitemap `i18n` option. A plain language
   link in the header; never redirect by `Accept-Language` or location (no
   detection, no tracking).
3. **Generated pages in Spanish only when the product speaks Spanish.**
   Propose localized metadata upstream: an optional `i18n` block in preset
   and theme JSON (for example `"i18n": {"es": {"name": "…",
   "description": "…"}}`), validated by the owning repo and read by the
   shell (Layout Picker) and by this site's sync. Until then, `/es/layouts`
   and `/es/themes` show Spanish chrome with English product names and an
   honest note.
4. **Docs.** English only until HorneroOS/docs adopts a translation
   workflow; Spanish docs routes, when they exist, fall back to English per
   page with a visible "not translated yet" banner.

## Effort and order

| Step | Work | Depends on |
| --- | --- | --- |
| 2 | i18n config, `/es/` copies of 4 hand-written pages, header switch, hreflang, sitemap | a Spanish copy review by a native speaker (the maintainer) |
| 3 | `i18n` blocks in shell presets and config theme packs, sync support here | shell/config PRs with tests |
| 4 | Docs translation workflow | HorneroOS/docs decision |

## Decision

Do step 1 now (already true of the current pages), start step 2 when the
hand-written copy stops changing weekly, and only do step 3 through the
product repositories.
